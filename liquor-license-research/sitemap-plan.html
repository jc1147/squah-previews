Sitemap and canonical work order

90% of the site points away from itself. The fix is mechanical on 859 pages and dangerous on 49. This is the corrected plan, after 24 independent reviewers refuted all ten of my original tasks.

The problem

The sitemap submits the page the site disowns

Of 1,006 live pages, 908 carry a canonical tag pointing at a different URL, and not one of those 908 targets appears in any of the ten sitemaps. Both URLs serve the same page. The sitemap advertises the copy the site itself rejects.

sitemap says  /cities/agoura-hills/agoura-hills-liquor-licenses.../
page says      /cities/agoura-hills-liquor-licenses.../

The rule is exact: drop the middle folder segment, keep the trailing slash. It reproduces on all 908 pairs with zero exceptions, across both the city and county templates.

Google has already chosen. 99 of your ranking keywords sit on the canonical targets against 12 on the sitemap URLs. So the sitemap moves, and the canonical tags stay exactly as they are.

The finding that changed the plan

49 of the 908 are a trap

859 Safe to repoint

Target returns 200 with no redirect. Mechanical, low risk.

49 Hold, do not touch

Target already redirects today. 34 city, 15 county.

Why this matters

41 of those 49 redirect straight back to the URL the plan deletes. Issuing the planned redirect on them closes an infinite two-node loop and takes 41 live pages offline for users and for Google. The other 8 point somewhere else entirely.

I had checked 11 pages by hand, seen all of them clean, and told you the rule was safe. At a 5.4% fault rate an 11-page sample misses this more than half the time. All 908 have now been fetched individually, one at a time, with redirects disabled.

The corrected sequence

Ten tasks, in this order

T0Pre-flight the target sideblockingnew

Fetch all 908 canonical targets with redirects disabled. Only the 859 returning a clean 200 are eligible for anything downstream. Done already, and the hold list is on file.

Was a footnote. The reviewers were unanimous that this is a task, not a note, because every later step silently assumes it.

T1Snapshot everything you are about to changeblockingrevised

Archive all ten sitemap files plus robots.txt, and export a four-column map of URL, canonical, title and meta description for the 1,006 live pages. Hash each file at capture time and store the hashes.

Was unsatisfiable. It asked for a byte-for-byte match, but two sitemaps carry a server-generated timestamp that drifts on its own, so a perfectly faithful archive would fail the check. It also captured no titles, which a later task claims to roll back from it, and never archived robots.txt at all.

T2Repoint the city and county sitemapsblockingrevised

Replace 859 nested entries with their canonical targets. Leave the 49 held entries exactly as they are. Verify by diffing the emitted entries against the pairs file before fetching anything, then fetch every entry with redirects disabled.

Was unsafe on 49 URLs, and its pass condition could not catch its own worst case: the slash-less form of a target also returns 200, so a slash-stripped sitemap would have passed a zero-non-200 check.

T3Put Type 42 in the navigationrewritten

Add Type 42 to the licence-type navigation, which today lists only 20, 21, 41, 47 and 48. No sitemap change.

I had this wrong three times. I called that page an unlinked orphan earning traffic. It is a redirect, and its destination is already in your sitemap, already indexed, already self-canonical. The keyword data had recorded the old URL. The upside I promised was not real.

T4Resolve the duplicate-title twinsretargeted

Runs after T10, not before. Each of the 13 clusters is four live URLs, not two. Target the flat pair, which is what actually gets indexed.

Pointed at the wrong URLs. It listed the nested copies that T2 removes and T10 redirects away. On three clusters the site already redirects into the very URL the task said to delete.

T5Write 149 missing meta descriptions

Unique per page, varied by the page's own city, county or licence type.

T6Trim 523 over-length titles

Ship in batches by template and watch impressions, so a bad pattern shows on 50 pages rather than 523.

T7Fix the homepage canonicalrevised

It currently reads as a bare slash. Set the stored field to the full absolute URL, which also fixes the og:url tag printing the same value.

Verification measured the wrong thing. "Absolute, www, HTTPS" goes green on a canonical pointing at the wrong page.

T8Fix or drop the empty products pagerevised

It returns "No products found" while sitting alone in a sitemap at priority 0.95. If you drop it, remove the child sitemap from the index in the same change.

Two details wrong. 0.95 is the second-highest priority, not the highest. And "no longer in any sitemap" would pass while leaving a dead child file listed in the index.

T9Allow the AI crawlersrewritten

Add the six agents as extra user-agent lines on the existing wildcard group, so they inherit your existing rules.

Would have broken your access control. A named group inherits nothing from the wildcard, so separate stanzas would have exempted all six from the rules blocking your admin and login paths. It also grants no new access, because the wildcard already allows them.

T10Redirect the nested duplicates awayrevised

Only the 859 eligible pairs, only after T2 is confirmed processed, and in both the slash and slash-less form of each source.

The dangerous one. As written it would have closed an infinite loop on 41 pages. It also covered half the source URLs it needed to.

Before anyone ships

Three standing rules

Never drop the trailing slash. The measured rule keeps it on both templates. A slash-dropping redirect across 908 URLs would 404 or loop.

Never ship T2 and T10 together. Two signals about the same URL pair in one release make any traffic movement impossible to attribute.

Never noindex the duplicates. A noindex on a page whose canonical points elsewhere can suppress the target too. The canonical tags are already doing this correctly.
